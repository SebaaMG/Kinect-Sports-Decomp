# Kinect Sports decompiler research and measured customizations

The stable imported program uses Ghidra language `PowerPC:BE:64:A2ALT-32addr`, compiler spec `default`, 32-bit pointers, 64-bit registers, and big-endian memory. This is a generic Power ISA/Altivec language, not an Xbox 360 Xenon-specific language. The XEX metadata alone does not validate its instruction coverage or inferred C types.

## Applied to the current read-only exporter

- Use Jeff function starts and sizes to rebuild the specific body being queried. Clear incorrect `CALL_RETURN` overrides in the disposable analysis session. An audit found that clearing all 101 Ghidra no-return flags was overly broad. Preserving them truncated seven of 111 exports; tracing the affected calls identified seven false no-return callees. The exporter now clears only those seven. Its 111 C files are byte-identical to the prior broad-clear export, while 94 other flags remain intact. This is evidence for the sampled callers, not a proof that the remaining flags are correct for every game function.
- Mask verified relative `bl __savegprlr_14..31` instructions with a temporary `nop` for decompiler analysis. This recovered the true first parameter in three inspected functions, improved one constructor from 80.79% to 87.11% under `/O2`, and changed seven of 111 Boxing-reference exports. The XEX and Jeff target objects remain unchanged.
- Apply the Jeff-identified `strstr` signature (`char *(const char *, const char *)`) at `0x82F64C68`. Together with a local pointer-return signature for the sport selector at `0x82486A20`, Ghidra emits actual string searches and named string literals rather than opaque calls and sign-extended numeric addresses. With the same MSVC 10224 `/O1` compilation, code match improved from 53.51% to 75.88% for that selector. Eight of the 111 Boxing-reference C exports changed under the CRT typing trial; not all eight have matching measurements yet.
- Regenerate task packets from **all** current Jeff assembly units, including the isolated units. An earlier packager only read the original monolithic unit and produced empty assembly after Jeff split it. The corrected 111 packets have nonempty C and assembly.

## Evaluated but not promoted

- Replacing a verified `b __restgprlr_*` at a function's final instruction with temporary `blr` changed no C across 111 Boxing-reference functions. It is therefore not included in normal export.
- Typing only the float constant at `0x821CC160` made a constructor's C more readable but lowered its `/O1` code match from 92.36% to 90.20%; Ghidra still treated the destination field as an integer.
- A provisional 0x360-byte object struct with a float field at offset `0x280` emitted a correct float store, but lowered the constructor's `/O1` match to 78.41%. The signature and layout are not sufficiently established to apply globally.

## Xenon language and MSVC switches

The community [GhidraXenon extension](https://github.com/freeqaz/ghidra-xenon-extension) provides `PowerPC:BE:64:Xenon` and VMX128 SLEIGH definitions. Its release `v12.1` states 77 VMX128 opcodes and includes `RecoverMSVCSwitchTables.java`. That script targets Xbox MSVC's 16-bit relative offset switch tables, which Ghidra's generic PowerPC analyzer may miss. The extension README says its standalone package does not patch Ghidra's core `PowerPCAddressAnalyzer`; the author's [full fork](https://github.com/freeqaz/ghidra) does.

The extension ZIP was downloaded, SHA-256 `cdbdddf60f23f4a53d6e7f9bc020720a3c35401ca6989085190fbf77e59604d8`, and installed under the SSD Ghidra installation. A **separate** Xenon-language project was imported with automatic analysis disabled. The XEX loader reported an LZX input error, as it did for the stable project. The full `.text` range (`0x82230000`, `0xF1386C` bytes) SHA-256 matched Jeff's extracted PE in **both** the stable and Xenon projects: `0d6f184304e15ae3da2e05c8ce4131f07a85b7e7284f64ae23db09776982c0ee`. Four inspected opcodes that generic `A2ALT-32addr` could not decode became `vsubfp128`, `vor128`, and `vaddfp128` under Xenon. Three VMX-heavy functions whose generic C ended in `halt_baddata()` produced full C bodies of 3.4–8.1 KB under Xenon. These bodies still contain unknown types and vector user-operations; they are seeds, not verified source or behavior.

Jeff assembly contains 132,782 VMX128 instruction lines. `scripts/classify_vmx_functions.py` assigned 132,750 of them to 6,339 Jeff function ranges; 32 lines were outside those ranges and require boundary review. The private index is `analysis/vmx128-functions.json`. `scripts/decompile_vmx.sh` routes an address/size list to the Xenon project. None of the 111 directly Boxing-string-referencing functions contains a VMX128 instruction, so their existing scalar export remains suitable; the wider Kinect/game code has extensive VMX128 and should use Xenon C as its first candidate.

The MSVC switch script was tested at `0x822C0B24`: it recovered a 10-entry halfword table and added 10 computed-jump references, including a zero entry that the default analyzer misses. The generic project initially warned about the jump table. However, our Jeff-sized `DecompileBatch` already reconstructed a full `switch` for function `0x822C0AA0`, and running the community script before that batch did **not** change its C. This script is useful for improving the persistent analysis graph and other functions, but it is not a measured match improvement on that sample. A different switch at `0x8236FB90` uses `lbzx`; the community script explicitly skipped it because its supported pattern requires `lhzx`.

The [Dance Central 3 decomp tooling](https://github.com/freeqaz/dc3-decomp/tree/main/tools/ghidra) offers further patterns that fit Kinect Sports: export both RAW and HIGH P-code to diagnose what the SLEIGH instruction model says versus what the decompiler optimized; inspect switch and sign/zero casts against original PPC bytes; and compare a reconstructed header layout against Ghidra's data-type manager. These are analysis aids, not automatic binary matches. `DecompileBatch.java` now has an optional `--export-pcode` mode for bounded RAW/HIGH dumps alongside C; a three-function scalar smoke test passed and produced a 494-line P-code file for the Boxing Camera constructor. The Xenon project's full auto-analysis hit its 600-second limit but saved partial analysis. Afterward `scripts/decompile_vmx.sh` successfully exported C and RAW/HIGH P-code for all three sampled VMX functions: 5,374, 800, and 1,911 P-code lines. Their C changed mostly in symbol naming and formatting compared with the prior no-analysis Xenon export; no improved object match has been measured.

## Remaining decompiler work

1. Compare a larger scalar/VMX corpus between the stable and Xenon projects. Equal full `.text` hashes and three VMX functions establish clear decoding benefit but do not establish correctness across the binary.
2. Recover MSVC switch edges in the analysis graph, then identify functions where the reconstructed C actually changes. Extend pattern coverage to the `lbzx` form only after validating table bounds and targets.
3. Build a trusted signature library from Jeff's named CRT and XEX imports; apply only symbols whose address and ABI are supported by the binary. Re-run the same matching corpus after each family of signatures.
4. Infer class layouts from multiple constructors, vtables, callers, and runtime evidence, then benchmark compiled output. A single constructor is insufficient to validate a whole class layout.
5. Extend the false no-return audit to additional subsystems and keep automatic checks for empty assembly/C and suspiciously truncated functions.

There is no finite setting that yields original source or immediate 100% object matches. The practical objective is higher quality initial C and fewer compiler/objdiff iterations per verified function.

## Additional community leads (24 September 2026)

- [`xdzleo/xenon-jumptables`](https://github.com/xdzleo/xenon-jumptables) documents several Xbox 360 MSVC dispatch patterns missing from stock switch recovery: conditional-return bounds, in-place scaled or reloaded indices, `lbzx`/`lhzx` relative tables, and tables embedded in `.text`. Its [idiom catalogue](https://github.com/xdzleo/xenon-jumptables/blob/main/docs/idioms.md) directly covers the `lbzx` pattern our current recovery script skipped at `0x8236FB90`. Its implementation requires commercial IDA and produces tables for static recompilers; it is **not** a drop-in Ghidra decompiler extension. Porting the validated table-target logic to a bounded Ghidra script is promising. For Kinect Sports, measure how many new edges and changed C bodies it yields before claiming a gain.
- A Jeff assembly scan with `scripts/find_split_switch_candidates.py` found **1,091** `bctr` instructions immediately followed by a Jeff function boundary: 4 with nearby `lbzx`, 1 `lhzx`, 25 `lwzx`, and 1,061 without one of those loads in the preceding 12 lines. These are triage candidates, not 1,091 confirmed bad boundaries; indirect tail calls and distant table loads also occur. At `0x8236FB90`, Jeff ends a function immediately before `0x8236FB94`, which contains the first case body in the documented byte-table idiom. The private report is `analysis/split-switch-candidates.json`. Recovering the case targets and then repairing this split could materially improve decompilation, independent of renaming or C formatting.
- A bounded trial at `0x8236FB90` read the 48-byte table at `0x82194BB8`, checked every computed destination against the following Jeff code range, and found 42 distinct targets. Merely combining the two Jeff ranges or adding `COMPUTED_JUMP` references left Ghidra's C at 284 bytes with an indirect-call warning. Applying Ghidra's documented `JumpTable.writeOverride()` **after** creating the merged function produced 2,484 bytes of C with 42 explicit case labels. The trial source is `tools/RecoverByteSwitchTrial.java`; `scripts/promote_byte_switch_trial.py` records this C as a `review` seed and marks 41 Jeff subranges as `fragment` in the private ledger so they are not treated as independent functions. This is a control-flow recovery result, **not** a compiler match. The apparent six trailing zero table bytes may be padding or aliases; the caller's valid index bound remains to be verified.
- [`tomcl7/ghidra-fidb-xenonsdk`](https://github.com/tomcl7/ghidra-fidb-xenonsdk) provides Ghidra Function ID databases for several XDK releases, generated by [`x360-fidb-generator`](https://github.com/tomcl7/x360-fidb-generator). These could identify static SDK/library functions and improve names, call signatures, and caller analysis. The newest published database in the repository is XDK 9328, whereas the compiler being tested here is 10224; signatures must be treated as hypotheses and confirmed against Jeff, call sites, and bytes. Keep any SDK-derived data in the private lab.
- The XDK 9328 FIDB was tested on an isolated copy of the stable Ghidra project. It returned the expected names for four Jeff-known functions: `strstr`, `strncmp`, `memcpy`, and `memset`. A whole-project scan examined 38,119 Ghidra functions, hashed 19,603, and returned 2,621 candidate hits; 402 have one database candidate, while most are ambiguous. `tools/ScanXdkFid.java` creates the private `fid-scan.tsv`, and `scripts/import_fid_candidates.py` stores hits with score, library, and candidate count in the SQLite ledger. No FID name has been applied globally, and a unique database hit is still a hypothesis. The Ghidra function count differs from Jeff's 57,731 ranges because their boundary discovery differs.
- The [`GhidraXenon` release](https://github.com/freeqaz/ghidra-xenon-extension/releases/tag/v12.1) notes that the extension's switch recovery is a script, while the author's [full Ghidra fork](https://github.com/freeqaz/ghidra) patches `PowerPCAddressAnalyzer` for automatic MSVC switch recovery. Since our Jeff-sized export already emitted a full switch for the one tested halfword table, switching builds should be benchmarked on functions where the current C is genuinely incomplete.
- GitHub repository search for `"Kinect Sports" decomp` found only the existing `SebaaMG/Kinect-Sports-Decomp`; it did not reveal a public, title-specific symbol map or decompiler patch to import. This is a repository-search result, not proof that no private research exists.

## Whole-game autonomous pass

`scripts/export_full_game.py` indexes 57,731 Jeff function ranges and writes resumable C seeds and per-function states to the local lab SQLite ledger. The routing index sends 6,339 VMX128 ranges to the Xenon Ghidra project and the other 51,392 to the stable project. A systemd user service runs 200-function batches, stores C and logs privately, and retries failed rows up to three times. `scripts/next_match_tasks.py` reads bounded, unverified work from the ledger. `scripts/audit_full_game_seeds.py` adds warning and suspicious-short-body flags after the export has stopped. A seed file is analysis output, not a verified source reconstruction; `match_percent` remains NULL until an object comparison is recorded.

The baseline pass has 52,147 `seed_ready`, 5,439 `review`, 27 `boundary_review`, 41 `fragment`, and 77 `failed` entries after classifying all opaque `vector…()` calls. After selecting the measured revisions, the effective counts are 52,333 `seed_ready`, 5,253 `review`, 27 `boundary_review`, 41 `fragment`, and 77 `failed`. All 57,731 Jeff entries have an assembly range; 57,614 have C files. The 41 fragments belong to one validated byte-table switch and are excluded from task selection. The one exact objdiff code match at `0x82FA5958` predates this pass and is recorded separately with compiler, flags, and evidence path; it does not imply the other seeds compile or match.

The union of Jeff ranges covers 99.22% of `.text` bytes. Of 30,241 gaps, 29,976 are 4 bytes; only one gap exceeds 32 bytes (736 bytes at the end of `.text`). This indicates that the list spans almost all of `.text` by bytes, but does not establish that every range is a valid independent function. Confirmed switch fragments demonstrate the opposite for at least one region.

## Community follow-up, 24 September 2026

- [`xdzleo/xenon-jumptables`](https://github.com/xdzleo/xenon-jumptables) is a relevant new source for Xbox 360 switch idioms. It recognizes bound checks using conditional returns, copied or scaled index registers, byte/halfword relative tables, and tables inline in `.text`. Its author reports 74 versus 6 IDA-auto tables on one retail title and 186 versus 74 on another; those are results on other games, not a Kinect Sports measurement. The implementation is an IDAPython pass and IDA is not installed here, so the practical route is to port and verify its idiom checks against our Jeff assembly and extracted PE. The source and documentation were cloned privately to the SSD. Its boundary-grid method applies to static recompilers and is only a research lead for our Jeff boundaries.
- A read-only triage script, `scripts/audit_switch_candidates.py`, found 551 Jeff ranges containing both `bctr` and a byte/halfword indexed load. Of these, 55 already carry C-review flags. The validated `0x8236FB68` byte-table switch is on this list. This is a broad shortlist: the instructions can be unrelated, and many `bctr` uses are virtual dispatch. Each table requires a proven bound, base, scale, and in-`.text` targets before changing Ghidra's control flow. The shortlist is stored privately as `analysis/full-game-export/switch-candidates.json`.
- The latest [`freeqaz/ghidra` switch fix](https://github.com/freeqaz/ghidra/commit/9434f1c1) (9 June 2026) injects the assumed switch index into MSVC switch recovery. This behavior is in the full fork, not the installed extension. A fresh, isolated import and a comparison on the 55 flagged candidates would establish whether building the fork saves work here; the extension alone does not provide that patch.
- The 15 September 2026 [`dc3-decomp` audit](https://github.com/freeqaz/dc3-decomp/commit/4825b22c) found 24 of 38 zero-scoring rows structurally unscoreable because of ICF aliases or placeholder/object attribution, rather than poor C. This reinforces the need to confirm original-object ownership and folding before treating a persistent 0% result as a source-code problem. It does not change our current match count.
- The upstream `GhidraXenon` SLEIGH model emits `vectorConditionalSelect`, `loadVectorLeftIndexed128`, and many other `vector…()` user operations. The earlier narrow audit flagged 1,900 C seeds; the revised audit recognizes all such calls and flags 3,727 effective seeds. Better decoding has produced C bodies, but semantic lifting and compiler matching for remaining operations remain unverified.

## Xenon register alias and `vsel` pilot

The community `GhidraXenon` language defines VMX128 registers `vr0..vr127` starting at SLEIGH register offset `0x10000`, while its inherited AltiVec instructions use `vs32..vs63` at `0x4200..0x43ff` for the physical vector registers 0..31. A mixed instruction stream therefore does not share dataflow between VMX128 and AltiVec operations on the same hardware register. In `0x82805520`, baseline RAW P-code wrote AltiVec `vsel` to register `0x42d0` but VMX128 `vrlimi128` read `0x100d0`, although both instructions name physical v13. This is stronger evidence than a cosmetic difference in decompiled C.

An isolated experimental patch, [the source diff](../tools/xenon-register-alias.patch), maps VMX128 v0..31 to existing `vs32..vs63`, defines v32..127 at `0x4400`, and replaces the AltiVec `vsel` user operation with `A & ~C | B & C`. Ghidra's SLEIGH compiler accepts it. A read-only five-function comparison completed 5/5 exports on each language version and removed the `vectorConditionalSelect` call from all five patched C outputs. At `0x82805520`, the patched C passes the output of `vsel` into the following `vrlimi128`; baseline C treated the latter's vector input as an unrelated incoming register. The private baseline, patched C, and RAW/HIGH P-code are under `analysis/vsel-trial/` in the local lab. The installed language was restored after each test and its `.sla` SHA-256 matches the saved original.

The subsequent Xenon revision exported 6,271 of 6,339 ranges. It changed 4,767 C files from the original language export. The 82 failures fall back to the original seed where available; 38 of those were newly introduced failures. The source patch also models `vaddfp` and `vsubfp` by four float lanes. A 50-function comparison exported all 50 under both languages, with 45 changed C files. These figures measure decompiler output, not compiler matches. The baseline ledger stays immutable and `seed_selection.py` chooses the verified-on-disk revision for each task.

## AltiVec semantic follow-up

The current upstream `GhidraXenon` source already models VMX128 `vand128`, `vandc128`, and `vcmpeqfp128`, but leaves their ordinary AltiVec counterparts as opaque user operations. The local upstream HEAD still equals the February 2026 extension checkout (`3db42fe`) as of 24 September 2026. The [second patch](../tools/xenon-altivec-semantics.patch) copies the known bitwise semantics and the extension's four-lane float equality mask into the non-dot instructions. It deliberately leaves `vcmpeqfp.` unchanged because its CR6 side effects need separate validation. It also leaves `vmaddfp` and other fused float operations opaque rather than silently changing rounding behavior.

Jeff assembly locates `vcmpeqfp` in 707 Xenon ranges, `vand` in 169, and `vandc` in 43; their union is 834 ranges. An isolated 45-function trial exported 45/45 on both language builds and changed 44 C files. Opaque calls for these operations fell from 74 to one in that sample; four patched C files newly mentioned memory address zero. The full targeted revision exported 821/834 ranges and changed 808 relative to the previous Xenon revision. The 13 failures had also failed in the previous Xenon pass. In the 821 successful exports, opaque calls fell from 1,605 to 21, the remainder mostly from the untouched dot compare. The selector chose 795 changed files, kept earlier C for 13 unchanged outputs, and rejected 13 new zero-memory references. No new C body grew by more than 1.45 times in this pass. The SLEIGH compiler accepted the patch, and the installed Xenon `.sla` SHA-256 is `f722ac586a9990953b9aef3e000b36290236be65e35710104d6d7b8cf48e6f26`.

Run `python3 scripts/audit_seed_revisions.py` to verify hashes and current selection. The private sample and logs are under `analysis/altivec-pcode-trial/`; the full targeted output is under `analysis/full-game-export/revisions/xenon-altivec-v2/`. A Ghidra C change does not establish semantic equivalence or object matching. The exact code-match count remains one; compiler fingerprinting and a rebuilt vector candidate are still needed before attributing matching speedups to these changes.
